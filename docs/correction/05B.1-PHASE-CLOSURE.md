## Final Report

### IDEMPOTENCY SEMANTICS
Fixed. `postLedgerTransaction()` now:
1. Checks existing IdempotencyRecord before any write
2. If COMPLETED with matching fingerprint → returns cached result
3. If COMPLETED with DIFFERENT fingerprint → throws `IDEMPOTENCY_CONFLICT`
4. If PENDING → throws error (concurrent in-flight)
5. If not exists → claims + writes in single PostgreSQL `$transaction`
6. On unique constraint violation → reads existing, verifies fingerprint, returns cached result

Payload fingerprint: SHA-256 hash of sorted `accountId:accountType:entryType:amount` per entry, prefixed with currency.

### ACTUAL LEDGER MODEL STRUCTURE
- `FinancialLedger`: Individual ledger entries (debit/credit). Each row = one entry. Grouped by `referenceId` (transaction identifier) and `idempotencyKey` prefix.
- `WalletBalance`: Denormalized balance cache with optimistic locking (`version` field).
- `IdempotencyRecord`: One row per unique idempotency key. Stores fingerprint in `metadata`, result in `resultPayload`.

Transaction grouping: All entries sharing the same `referenceId` + `referenceType` belong to one logical transaction. Balanced invariant: SUM(CREDIT amount) = SUM(DEBIT amount) per referenceId.
